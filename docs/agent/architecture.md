# Architecture notes

The root [README](../../README.md) is the primary architecture reference — read
its "Non-negotiable architectural constraints" and "Cross-module data model"
first. This file holds only invariants and decisions that are **not** written
there, or that need a sharper statement for agents.

## Invariants (candidates for contract tests — see improvements.md)

1. Every Supabase client is created through `src/lib/supabase/*` with `db.schema = 'greendogops'`.
2. No migration creates or alters objects outside `greendogops`.
3. No routine is executable by `anon` / `authenticated`; `greendogops.rls_audit()` returns zero rows.
4. `SUPABASE_SERVICE_ROLE_KEY` / `createAdminClient()` are never reachable from client components or `NEXT_PUBLIC_*`.
5. Every exported Server Action in an `actions.ts` re-checks permissions before writing.
6. Every cron route checks `isAuthorizedCronRequest` (`src/lib/auth/cron.ts`).
7. Adding a module touches `ModuleKey`/`MODULES`/`ROUTE_MODULES` in `permissions.ts`, the nav in `app-shell.tsx`, and `MODULE_ICONS` in `src/lib/shared/module-icons.ts`.
8. Every write to `ops_task` goes through `src/lib/worklist/tasks.ts`. Every notification goes through `emitEvent()` (module events, routed by rules — `src/lib/notify/emit.ts`) or `publishNotification()` (one chosen login — `src/lib/notify/publish.ts`); every event type is registered in `src/lib/notify/registry.ts`. Work-center and notification tables are service-role only and every read filters to the signed-in user (Admin ▸ Notifications excepted).

### 2026-10-14 — PTO & Timekeeping Rules page is generated, versioned and signed off (go-live item 26, plan §I)
- **Decision:** `/hr/pto-rules` is built by `buildRules()` (`src/lib/pto/rules.ts`) from the same constants and functions the calculations use; every worked example runs the real engine (`computePeriod`, `checkMeals`, `parseSelfRequest`, `payPeriodFor`, `src/lib/pto/annual.ts`) on fixed sample data. `rules.test.ts` pins the outputs, so a rule change that alters an example fails a test and must be reviewed.
- **Sign-off:** `rulesVersion()` = first 12 hex of SHA-256 of the rules JSON. Sign-offs are `audit_log` rows (`timekeeping_rules.signed_off`, `metadata.version`) — no new table. A changed rule = a new version, shown as "not signed off".
- **Honesty:** the yearly cycle (Jan 1 reset, +2 tenure, proration, payouts) is labelled "Policy — applied by HR until automated"; `src/lib/pto/annual.ts` holds its pure rules for the future job (improvements.md).
- **Not done:** a PDF copy in Resources (plan §I) — the page is the source; add the PDF once signed off if Resources search needs it.

### 2026-10-14 — Ops owns the PTO balance; approvals deduct in the database (migration 0246, go-live items 23–24)
- **Decision (owner):** the HR profile's `pto_used` / `pto_available` (days) are the opening balance — no separate load (item 24). From 0246 on, Ops keeps them current: approving a paid request deducts its days immediately; deny / reopen / delete returns them. The nightly HR-roster sheet sync no longer writes any PTO column.
- **How:** one BEFORE INSERT/UPDATE + AFTER DELETE trigger on `person_time_off` (`person_time_off_balance`) computes what the row should hold (`approved` + `balance_tracked` + kind `pto`/`vacation` → `coalesce(pto_days, calendar days)`), applies the difference to `person_employment`, and stores it in `pto_days_deducted`. Every approval path (Time Off queue, grid, HR profile, Slack buttons) is covered without TypeScript changes. The logic is inline (no helper functions) so the editing roles need no EXECUTE grant. `src/lib/pto/balance.ts` `deductionDays` mirrors the rule for previews.
- **Legacy rows:** the 502 requests already `approved` when 0246 ran are `balance_tracked = false` — the sheet's "PTO used" already counted them, so they never move the balance. Pending When I Work imports are tracked; their kind came in as `time_off` (unpaid), so approvers choose paid/unpaid and the days in the queue (0 days = already counted).
- **Audit:** `pto_ledger` (append-only, service role) gets a row for every allotment/used/available change on `person_employment`, tagged `time_off` + request id (via transaction-local `greendogops.pto_*` settings) or `manual`, with `auth.uid()`.
- **Fixed with it:** the HR profile form used to recompute "Used" (all approved requests, all years, unpaid included) and "Remaining" (`pto_policy_allotment` − used) on *every* save — the sheet sync had been masking it. It now shows the stored values and writes them only when HR changes them (`ptoBalancePatch`, `*_was` hidden fields).
- **Also:** the When I Work import is now insert-only (`ignoreDuplicates`), so a re-poll can never reset a request approved in Ops (which would now also give its days back).

### 2026-10-14 — Payroll periods, approval, lock and export (migration 0245, go-live item 21)
- **Decision:** hours and premiums are computed at read time by one pure engine (`src/lib/payroll/ca-rules.ts`) from the effective punches; nothing stores computed hours except the **approval snapshot**. The export is built only from those snapshots, so the file always equals what an approver signed off. If live totals differ from the snapshot, the approval is "stale" and blocks the lock.
- **Rules encoded:** workweek Sun–Sat (aligned with the biweekly periods anchored 2026-09-20); daily OT > 8 h, DT > 12 h; 7th consecutive workday in the workweek: first 8 h OT, beyond DT; weekly OT > 40 h counts only regular hours (no double counting); one meal premium per day (first meal by the end of the 5th hour, ≥ 30 min, second by the 10th; waivers from `meal_waiver`); one rest premium per day when the employee worked ≥ 3.5 h and answered "No" at clock-out. Unknown FLSA is treated as non-exempt (premiums apply) and flagged in the export.
- **Guards in the database:** `timecard_approval` insert/delete only while the period is open, never update; `time_punch_adjustment` refused for dates in a locked/exported period; `payroll_export` append-only. Reopen (Owner/Admin, reason) is the only way back.
- **Interim format:** `ops_totals_v1` is not the ADP RUN import. When the RUN header row (#19) and pay codes (#20) arrive, add a new format alongside it and refuse employees without an `adp_employee_id`.

### 2026-10-13 — ADP RUN Employee ID + payroll readiness (migration 0244, go-live item 18, plan D12/D13)
- **Decision:** `person_employment.adp_employee_id` (letters/digits/dashes ≤ 20, unique when set) is payroll data and joins `COMPENSATION_FIELDS`: no column grant to `authenticated` (any active login can read granted `person_employment` columns), read/written with the service role after `canViewAllCompensation` or the own-record check, blocked for non-full Ask Ziggy tiers. ### 2026-10-13 — Automatic attendance graded at read time; Time & Attendance dashboard (migration 0243, go-live item 16)
- **Context:** the plan proposed an `attendance_record` table. During the shadow run most staff don't punch in Ops yet, so stored "missed" grades would be wrong, and a second attendance table would duplicate `sched_assignment.attendance_status` (AGENTS.md §4).
- **Decision:** grade at read time, store nothing. `src/lib/timeclock/attendance.ts` (pure): match each person's effective-punch sessions to their published shifts (the clock-in's `assignment_id`, else the nearest start the same day; the rest is unscheduled work) and grade each shift: pto, upcoming, not_in_yet, missed, working, incomplete, left_early, completed, plus late / very late minutes. Thresholds and the go-live switch are `app_setting` rows (0243, Admin ▸ Settings ▸ Time clock). `gradeRange()` / `systemAttendance()` in `attendance-server.ts`. Scheduling ▸ Time & Attendance (`/schedule/time-attendance`, approvers + Schedule Admins) shows each clinic's day live, with the punch-match rate and unscheduled work, in shadow mode too. Only from `timeclock.attendance_from` (blank = off; owner chose shadow first) do grades feed `effectiveAttendance()` for **unmarked** shifts (attendance page, HR attendance summary, grid badges and menu) and do the 5-minute producers send `attendance.missed_shift` (same dedupe key as a manual No-show) and `attendance.late` (batched). A manager's mark always wins; dates before the switch keep the old "unmarked = present" rule, so history is never re-graded.
- **Consequences:** missed maps to Absent (a manager can mark No-show), late / very late to Late, left early and missing clock-out to Present (timecard issues). A grading failure falls back to manual marks only (`safeSystemAttendance`). Reliability v2 (graded deductions) is still the old weight table — improvements.md. Verified on staging end to end (grades, mapping, alerts once, restore). 0243 applied to staging and production 2026-10-13 before the app code (`attendance_from` blank = shadow mode; `rls_audit()` 0 rows).

### 2026-10-13 — Meal-period waivers: versioned documents, e-sign and revoke in My Time (migration 0242, go-live item 12)
- **Decision:** the two waivers (6-hour; second meal ≤ 12 h) are native policy documents seeded with fixed ids (`MEAL_WAIVER_DOCUMENT_IDS`) as DRAFT wording, visible to HR roles only, edited/versioned in Resources like any policy. `meal_waiver` records one row per signature bound to the exact `resource_document_version`; a trigger allows only revoking (the database stamps `revoked_at`), never edits or deletes; one active waiver per person and kind. My Time ▸ Meal waivers (non-exempt / unknown-FLSA staff only) shows the current version's text, needs a tick box plus the typed first + last name (`signatureMatches`), and refuses a stale version. `meal_waiver_in_force()` (SQL) and `waiverInForce()` (TS) give the waiver in force at a moment — the payroll meal rules use the shift's time, so revoking never changes past shifts. Status shows on the HR profile's Onboarding tab (Employee acknowledgements). Everything is off until an Admin sets `timeclock.meal_waivers_live` (Admin ▸ Settings ▸ Time clock).
- **Consequences:** HR / payroll must review the wording and flip the setting; editing a document creates a new version, and new signatures bind to it (existing signatures stay on the version they signed). `meal_waiver` is service-role only and blocked in Ask Ziggy. Applied to staging and production 2026-10-13 before the app code: `rls_audit()` 0 rows, both documents + versions seeded, setting off, function md5s identical.

### 2026-10-13 — Time clock: location check, off-site approval, adjustments, queues (migration 0241)
- **Context:** Gate 1 item 5 (plan D6, D9, §F). Punches are append-only, so approvals and corrections cannot be columns on `time_punch`.
- **Decision:** the check runs in TypeScript (`evaluateLocation`, pure and unit-tested; IPv4/IPv6 CIDR in `ip.ts`) and its result and evidence are passed to `record_time_punch()`, which requires a note for `off_site` and sets `needs_approval`. Decisions live beside the punch: `time_punch_review` (one per off-site punch; reject also voids it) and `time_punch_adjustment` (`add` / `void`, append-only, reason required, one void per target by unique index). `time_effective_punches()` (SQL) and `effectivePunches()` (TS) both compute punches − voids + adds; the clock state uses the effective set, so a manager-added clock-out closes a session. `p_abandon_previous` lets someone still "working" from > 8 h ago start a new shift. Approver actions are atomic SQL functions (`review_time_punch`, `decide_time_correction`) called after `canApproveTime` and a no-self-approval check, and audited. A clinic with no geofence/network is `not_checked`, so nothing goes to approval before Admin ▸ Time Clock (item 6) is configured; mobile locations are `anywhere_logged` and never match another clinic's punch.
- **Consequences:** the 0240 → 0241 `record_time_punch` signature change was made by DROP + CREATE with defaulted extra parameters, so callers using the old named arguments keep working through PostgREST (verified on staging). Raw GPS/IP/UA kept per the owner's decision (security.md §12). Rejecting an off-site punch removes it from the timecard; the approver adds a corrected punch if work was done. Applied to staging and production 2026-10-13 before the app code: `rls_audit()` 0 rows, one `record_time_punch` version, function md5s identical on both; MPMV set to `anywhere_logged`, no networks or geofences yet.

### 2026-10-13 — Staff is the employee role, read-only in the database (migration 0239; supersedes the 0238 `employee` role)
- **Context:** 0238 (Gate 1 item 1) added a separate self-service `employee` role that `is_gdo_user()` excluded, on the plan's assumption that employees would not be Staff. The owner then gave all 70 remaining employees active Staff logins and confirmed that Staff *is* the employee role. Staff are read-only in the app, but `gdo_members_all` (FOR ALL) let any active login write most tables through PostgREST.
- **Decision:** retire `employee` (app code reverted; the enum value stays, `app_user_role_supported` rejects it and `viewer`; `is_gdo_user()` and the `visible_roles` check back to pre-0238). Make Staff read-only at the database level with three RESTRICTIVE policies per table (`staff_read_only_insert/update/delete`, created by `staff_read_only_policies(table)`), ANDed with the permissive ones so no other role or narrower policy changes. `protect_new_objects()` adds them to new tables; `rls_audit()` flags any table without them. Med Ops boards — the one place Staff legitimately write — now write with the service role after `ensureBoardUser()` (an audit of every user-client write found all others behind edit gates Staff never pass). Kept from 0238: `authenticated` cannot execute any `SECURITY DEFINER` function except `is_gdo_user`/`is_gdo_admin`, the 4 user-session callers use the service role, and `rls_audit()` checks it.
- **Consequences:** anything new that Staff may change (time clock, PTO requests, policy signing) must be a Server Action using the service role and acting only on `current.appUser.person_id`; a user-client write as Staff fails silently on UPDATE/DELETE (0 rows) or with 42501 on INSERT. Pinned by `baseline-grants.test.ts` and the `staff_*` probes in `scripts/security_rls_matrix.sql`. Applied to staging and production 2026-10-13, after the app code (`397d8d7`, Vercel `success`): 501 staff policies on 167 tables, `rls_audit()` 0 rows, `is_gdo_user` / `rls_audit` / `protect_new_objects` md5s identical on both; a new table on staging got all three policies (rolled-back probe).

The shared `/crm/contact/[id]` and `/crm/org/[id]` pages, which the layout cannot gate, now check the record's section module (`crmModuleForSlug`), and the `/crm` hub lists only accessible sections.

Data scope is separate: Ask Ziggy's Staff `general` tier still reads the schedule grid / calendar / planning views so Staff can ask about their own shifts. Notifications about a Staff member's own shift/PTO still reach them (subjects skip the module check in `audience.ts`). Migration `0237` mirrors the Recruiting default in the `ats_read` RLS predicate (Staff: off unless overridden); `scripts/security_rls_matrix.sql` pins it. Applied to staging and production 2026-10-13 (policy md5s identical, `rls_audit()` 0 rows on both).

### 2026-10-12 — Notification engine: events, rules, person-keyed Slack delivery, buttons (migration 0236)
- **Context:** the owner wants Ops to tell the right people about operational changes through Slack automatically (schedule, PTO, attendance, marketing events, tasks), configurable without code, with actionable buttons. The 0230 pipeline only addressed logins (22 of 94 employees) and every caller picked its own recipient.
- **Decision:** one engine. A module calls `emitEvent()` with an event type from `registry.ts`, subjects and a payload (render data only). The engine stores a `notification_event`, merges the admin rule (`notification_rule`) with the registry default, resolves recipients from the live directory (subjects, roles, module editors, scheduling departments, named people, eligible candidates, optional same-location), filters restricted (`sensitivity: module`) events to subjects + people who can open the module, and writes inbox rows (logins only) plus `notification_delivery` rows addressed to a **person** (`recipient_person_id`) or a channel. The dispatcher sends Block Kit cards, re-checks employment, Slack link and module access at send time, batches/coalesces, escalates, and stores `slack_ts` so `resolveCards()` can update a card once its record is handled. Slack buttons go to `/api/slack/interactions` (signing secret), are logged in `notification_action`, and apply through the same write rules as Ops. Slack OAuth installation was not built: one workspace, one bot token.
- **Consequences:** adding Slack to a module = one registry entry + one `emitEvent()` call. Payloads and templates must stay free of compensation, HR-file and clinical content; PTO notes are dropped from channel posts. Missed clock-in/out is not implementable without punch data (improvements.md). `registry.test.ts`, `audience.test.ts`, `plan.test.ts`, `rule-config.test.ts`, `slack-blocks.test.ts`, `signature.test.ts` pin the rules; `smart-scope.test.ts` keeps the new tables out of Ask Ziggy.

### 2026-10-12 — Policies become native, access-controlled, signable Ops documents (migration 0235)
- **Context:** the owner is moving policies off Google Docs. HR / Management must edit them in Ops, choose who can view each one, notify that group on save, and optionally require initials + date, recorded on the employee's HR profile.
- **Decision:** `resource_document` gains a TipTap JSON body (`content_json`, allow-listed by `sanitizeDocument()` on every save), `visible_roles` (NULL = everyone) plus named people in `resource_document_viewer`, and a version counter. Every save inserts an immutable `resource_document_version`; signatures point at a version, and `signature_from_version` decides which signatures still count (a minor edit keeps them; "require signature" raises the baseline). Two separate rules: **viewing** = recipients + HR / Manager and above (who manage everything); **recipients** (notified, asked to sign, counted in "X of Y signed") = everyone, or only the chosen roles/people — managers are not recipients of a document addressed to someone else. All writes go through `src/lib/resources/documents.ts` on the service role; authenticated users get read-only, visibility-filtered RLS. Ask Ziggy's passage search takes the asker's id, and the raw document tables are blocked from its SQL for every tier that cannot see every document.
- **Consequences:** a signed document can only be archived (FK `restrict`; `deleteResourceDocument` archives). The 22 Google sources were converted in place by `scripts/import_google_docs_native.mjs`; their PDF/link copies are `is_active = false` with `superseded_by`, and old `/resources/doc/<copy>` links redirect. Images are stored inline as data URLs (≤ 3 MB each, 12 MB per document) so each version is self-contained. `scripts/e2e_policy_documents.mts` (staging) and the 0235 block in `security_rls_matrix.sql` pin the behaviour.

### 2026-10-12 — Ask Ziggy: lookups yes, revenue reporting no (migrations 0233–0234)
- **Context:** the owner wants every employee to look up retail prices and what ONE client paid ("how much did X pay on 3/14?"), but not run revenue reports ("how much did Venice make on 3/14?"). Both read `ezyvet_invoice_line`, so a table grant cannot tell them apart. The owner also confirmed AI-provider privacy is not a constraint.
- **Decision:** bounded, service-role-only lookup functions (`client_summary`, `client_visits`, `patient_visits`) that resolve to at most 10 clients/patients per call, plus — for the General tier only — a TS guard (`lookupCallProblem`) that accepts them only as `name('literal')`, at most 3 per query, so no join or subquery can fan them out across every client. Retail prices come from `product_catalog` (no cost/markup/margin). `staff_directory` and `schedule_roster` give names and who-works-when without private fields or attendance notes.
- **Consequences:** a new per-entity money lookup must follow the same pattern (cap in SQL + listed in `GENERAL_LOOKUP_FUNCTIONS`); `smart-scope.test.ts` checks every listed function calls a capped `ziggy_*_codes` helper. Raw billing tables and `report_*` revenue views stay off the General allow-list.

### 2026-10-12 — Smart Report becomes Ask Ziggy, open to every employee
- **Context:** the owner wants one AI assistant for every employee (company knowledge, cross-location patient/client lookup, own schedule/PTO), with higher roles reaching more. Smart Report already had conversation, policy retrieval with sources, per-role scope and a learning loop, but was closed to Staff and lived under Reporting. Location-level scoping is explicitly not wanted ("location agnostic").
- **Decision:** rename to Ask Ziggy at `/ask-ziggy` with its own `ask_ziggy` module key (on for every role, per-user override). Roles stay as they are; Staff get a new `general` tier that is an **allow-list** (`GENERAL_ALLOWED_TABLES`) resolved against the live catalog, because a deny-list cannot keep revenue out of ~100 tables and column blocking is defeated by whole-row expressions (`to_jsonb(t)`, `t::text`). Questions about the asker are answered from server-fetched own records (`ziggy-context.ts`), never by SQL over other employees. Functions that execute SQL from a string literal are rejected for every tier.
- **Consequences:** a new table/view is invisible to Staff until added to the allow-list, and anything added must be safe to read in full (`smart-scope.test.ts` checks existence and money columns). Employee names, the roster, prices and per-client charges came next through purpose-built views and bounded functions (0233, below).

### 2026-10-12 — Required basic-info fields on QR capture forms (migration 0232)
- **Context:** QR capture forms (`/q/<token>`, `/lead/<token>`) let custom questions be Required, but the built-in contact block only enforced the name and "email OR phone", so event leads arrived without a way to follow up.
- **Decision:** `qr_form.require_email` / `require_phone` (default **true**, applied to all existing forms) and `require_pet_name` / `require_zip` (default false, only effective while `collect_pet_name` / `collect_zip` is on). One rule, `checkBasicAnswers()` + `basicRequirementsFrom()` in `src/lib/marketing/qr.ts`, is used by both public submit actions; the browser `required` attributes are a convenience only. Both the pages and the actions treat an inactive form as "no form" (default rules, no custom questions). `saveQrForm` only writes `require_*` when the `basic_fields` marker is posted, so a stale editor tab cannot clear them.
- **Consequences:** new basic fields need a `require_*` column, a branch in `checkBasicAnswers`, and a row in `BasicFieldsEditor`. Rules are pinned by `src/lib/marketing/qr.test.ts`. ATS forms already had per-question Required and are unchanged.

### 2026-10-09 — Dashboard becomes a per-user work center (migration 0230)
- **Context:** the home page was a grid of module tiles. Users need one place for what is waiting on them, recurring checks, and notifications, and the owner plans Slack workflows that create Ops tasks and vice versa. Only `person_interview.host_user_id` was a true per-user assignment; everything else was a shared queue.
- **Decision:** five service-role tables — `ops_task`, `user_notification`, `notification_delivery`, `reminder_rule`, `reminder_ack` — keyed on `app_user` (the dashboard is for logins). Module work is **projected** at read time, gated by `canAccessModule`/`canEditModule`, never copied into `ops_task`. Each source loads independently, so one failure becomes a warning. Slack → Ops: `/api/tasks/inbound` (bearer secret, idempotent on `(source, external_ref)`). Ops → Slack: DMs through `notification_delivery` and the 5-minute dispatcher, recorded before sending, never resent after a possible delivery, dark until `SLACK_DM_LIVE`; and workflow events to `SLACK_WORKFLOW_WEBHOOK_URL`, never echoed back for Slack-sourced tasks. Ops still does not read Slack messages (no `*:history` scopes). Smart Report always blocks these tables.
- **Consequences:** a new module event should call `publishNotification()` with a `dedupeKey`. A new work source is a `Source` in `sources.ts` with its permission gate. Notifying employees who have no login (most of them) needs a person-keyed recipient — see improvements.md.

### 2026-10-09 — Slack identity keyed on person (migration 0229)
- **Context:** Ops needs to DM employees (schedule changes, PTO decisions, interview assignments). Only 22 of 94 active employees have an `app_user` login, so a link on `app_user` would miss most staff.
- **Decision:** `person_slack_link` keyed by `person_id` (service-role only, deny-all policy). `slack_user_id` is the permanent identifier; email is only used to find it, and never a name. A partial unique index stops one Slack account being connected to two people. Rows are never deleted. Whether a person may be messaged (`person.status`) is checked at send time and not copied onto the link, so the `person_after_change` triggers stay the single source for offboarding.
- **Consequences:** any future sender (Phase 2 notification service) must use only `status = 'connected'` links and must also check `person.status` itself. The rules are pinned by `src/lib/slack/matching.test.ts`.

### 2026-10-09 — Texting via Twilio, service-role tables (migration 0228)
- **Context:** staff need to text candidates and employees; US carriers require A2P 10DLC registration, consent, and STOP handling.
- **Decision:** Twilio REST over `fetch` (no SDK). `sms_message`, `sms_opt_out` and `sms_consent` are service-role only (deny-all policy); the app reads and writes them after `canTextPerson`. Opt-outs are keyed by phone number, because STOP comes from a number, not a person. Consent is self-service only. On `/apply`, ticking the box writes an `sms_consent` row (older Indeed/website applications still count through the application's `sms_consent` answer). Anyone else opts in at the public `/texts` page, matched by mobile number + last name. Staff can remove consent but not record it (2026-10-12): carriers rejected the campaign (30923) when consent looked like an onboarding requirement and couldn't be verified. The feature stays dark until all Twilio env vars exist, and `SMS_LIVE` gates real recipients.
- **Consequences:** the `sms_*` tables must exist before the Twilio env vars are set in an environment. Adding a send path (e.g. scheduling-link texts) must go through `sendSmsToPerson` so the same rules apply.

### 2026-10-08 — Sensitive HR boundaries enforced in the database (migration 0227)
- **Context:** 0164's `gdo_members_all` let every active `app_user` (Staff included) read/write every table through PostgREST with their own token — salaries, reviews, discipline, the audit log — regardless of what the UI hid. OWASP ASVS L2 review.
- **Decision:** keep `gdo_members_all` as the floor, but replace it on the HR-file tables with role-aware policies (inline subqueries on `app_user`, no helper RPCs per AGENTS.md); drop table-level SELECT/INSERT/UPDATE on `person_employment` for `authenticated` and re-grant only non-compensation columns; make `audit_log` append-only (trigger) and service-role only; require AAL2 in `is_gdo_user()` once a user has a verified MFA factor. Staff on other people's HR profiles get the same restricted view Schedule Admins already had. See `docs/security.md`.

Changing role semantics in `permissions.ts` must be mirrored in the 0227 predicates — `scripts/security_rls_matrix.sql` (staging) and `permissions.test.ts` pin both.
